## 二、实现方式

### 2.1 技术路线

**核心模型**：阿里云百炼 `wan2.2-animate-mix`（万相-视频换人）

**判断依据**：题目要求"人物替换"，而这个模型的原生能力恰好是
*"在不改变原始视频的动作、表情及环境的条件下，将视频中的角色替换为指定图片中的人物"*。

选它而非图生视频（I2V）的关键理由：

| 对比项 | 视频换人 Mix | 首帧 I2V |
|---|---|---|
| 保留原片运镜/背景 | ✅ 原生保留 | ❌ 会重绘 |
| 输入自由度 | 2 个（图 + 视频），**无 prompt** | prompt 是巨大自由度 |
| 跨片段一致性 | 高 | 低（每段风格漂移） |
| 为单片段特调的可能性 | **架构上不存在** | 很容易滑向特调 |

> **最重要的洞察**：由于该模型没有 prompt 参数，
> "为片段 A 特调参数拿高分"这条路**在物理上被堵死了**。
> 用"减少自由度"来实现"保证可复用性" —— 这比靠自律可靠得多。

### 2.2 五阶段管线

```
[1] ingest       切片 + 归一化(1280px/24fps) + 平台约束预检
[2] character    人设图规整(尺寸/宽高比/大小/格式)
[3] style_align  按片段画幅补边对齐 ★
[4] transfer     wan2.2-animate-mix: submit → poll(15s) → download
[5] assemble     音频回接 + 对照视频生成
        ↕
[eval]  L1 客观 / L2 语义(VLM) / L3 跨片段稳定性
```

### 2.3 工程特性

| 特性 | 实现 |
|---|---|
| 阶段可独立运行 | `cli stage --stage X --clip A` |
| 幂等缓存 | `input_hash` 命中 manifest 则跳过，避免重复计费 |
| 模型可替换 | `Adapter` 协议 + 注册表；换模型不改 `stages/` |
| 离线可验证 | `MockAdapter` + `cli smoke`（无需密钥/素材） |
| 可诊断 | 异常携带 `stage` / `clip_id` / `request_id` |
| 成本可核算 | manifest 记录 `billable_seconds` + `estimated_cny` |
| 架构可守卫 | 测试自动拦截片段特判分支 |

## 四、Pipeline 设计的考量和侧重点

### 4.1 首要考量：题目把优先级写反了常识

常识是"把质量做到最高"，但题目明确说：

> *"对片段 A 和片段 B 用同样的 pipeline 都跑出 75 分 >
> 对片段 A/片段 B 特调出 90 分"*

**这是反直觉的。** 它要求我们**主动放弃峰值质量，换取稳定性**。

所以整条 pipeline 的设计准则只有一条：

> **消除片段间的自由度差异，让 A/B/C 走过结构上完全相同的路径。**

### 4.2 三个关键设计决策

#### 决策一：选一个"没有 prompt"的模型

`wan2.2-animate-mix` 的输入只有 `image_url` + `video_url`。

**这不是缺点，是本题最大的优点**：
- 不存在"为片段 A 调 prompt"的歧路（物理上不可能）
- 变量少 → 方差小 → 稳定性高
- A/B/C 天然走同一条代码路径

#### 决策二：把"画幅对齐"提升为独立阶段

官方 FAQ 明确：*"画幅不匹配是最常见的弱结果原因"*。

如果不做显式对齐：
- 片段 A 的人设画幅可能恰好匹配 → 高分
- 片段 B 不匹配 → 崩掉
- 结果：**A 90 / B 40 → 极差 50 分 → 完全违反 P1**

所以把对齐从"注意事项"变成**架构组件**（`stages/style_align.py`）：
- 显式出现在流水线上，评审一眼可见
- 对 A/B/C 一视同仁
- 可独立运行、独立验证

> **这是"用架构保证公平性"的具体体现。**

#### 决策三：用测试守卫架构约束

`tests/test_pipeline_structure.py::TestNoClipSpecificBranch`
会自动扫描 `stages/` 源码，**检测到 `clip_id == "A"` 这样的特判就直接失败**。

这把"可复用性"从口头承诺变成了**可执行的检查**。

### 4.3 侧重点总结

| 侧重 | 投入 | 理由 |
|---|---|---|
| **架构解耦** | 高 | 阶段独立运行 + 无分支 = 可复用性基础 |
| **评估体系** | 最高 | 题目明确"侧重评估" |
| 单个片段画质 | 低 | 题目明确"不侧重工作量/峰值" |
| 模型调参 | 极低 | 没 prompt 可调，且调参是特调行为 |

## 五、评估方案的设计和考量

### 5.1 三层设计及必要性论证

| 层 | 手段 | 回答什么 | 为什么不可省 |
|---|---|---|---|
| **L1** 客观技术 | OpenCV + scikit-image | 技术合格吗 | VLM 有随机性、要钱、无法 CI；且抓不到细微闪烁 |
| **L2** 语义质量 | VLM `qwen-vl-max` | 人换成功了吗 | **L1 有语义盲区**：换得干净 vs 根本没换，PSNR 无法区分 |
| **L3** 稳定性 | 自研 | **pipeline 挑片段吗** | **前两层都只给单片段分，无法回答题目真正的问题** |

**L1 的语义盲区论证**（这是必须加 L2 的硬理由）：

- 情况一：把主角换成别人，换得很干净 → PSNR 低，但**任务成功**
- 情况二：根本没换人，只加了个滤镜 → PSNR 高，但**任务失败**

**L1 无法区分这两种情况。**

### 5.2 核心设计：L3 一致性指数

题目口径 *"稳定 75 > 特调 90"* 需要被编码成数学。我们构造：

```
CI = mean / (mean + k·std),  k = 2
```

k=2 的含义：**std 每增加 1 分，相当于均值降低 2 分** —— 波动的代价是分数代价的 2 倍。

实测验证（`StabilityEvaluator` 真实输出）：

| 场景 | mean | std | **CI** | 判读 |
|---|---|---|---|---|
| 稳定派 75/75/76 | 75.33 | 0.47 | **0.9877** | 优秀 ✅ |
| 特调派 95/95/45 | 78.33 | 23.57 | **0.6243** | 差 ❌ |
| 特调派 90/88/30 | 69.33 | 27.82 | **0.5548** | 差 ❌ |

**特调派 mean 更高（78.33 > 75.33），但 CI 更低（0.62 < 0.99）** ——
正是题目"稳定 75 分胜过特调 90 分"的数学表达。

> 这个对比已固化为单元测试
> `TestStabilityMath::test_consistent_beats_volatile_despite_lower_mean`，
> 保证口径不被后续改动破坏。

### 5.3 最容易被忽略但最重要的一环：评估器自检

**问题**：你怎么知道你的评估器是好的？

**答**：用 `MockAdapter` 制造**已知缺陷**，验证评估器能检出。

`tests/test_eval_sanity.py` 的三条断言：
1. `jitter=0`（完美复刻）→ 各项应接近满分
2. `jitter=1.0`（亮度交替偏移 = 人为闪烁）→ `temporal_stability` **必须显著下降**
3. `blur=21`（强模糊）→ `sharpness` **必须显著下降**

**如果评估器对人为扰动毫无反应 → 评估器是坏的 → 所有分数都不可信。**

当前状态：**3 passed** ✅

### 5.4 诚实性设计（三条硬约束）

写进代码，不是口号：

| 约束 | 实现 |
|---|---|
| 未测到的指标不能用 0 分冒充 | L2 调用失败返回 `value=None` + `note` |
| 样本不足时不能说方差 | L3 在 `< 2` 片段时返回"无法计算" |
| 必须报最差片段分 | L3 输出 `worst`，不只报 `mean`（木桶效应是特调特征） |

已固化为测试 `TestNotMeasuredIsHonest` 与 `test_missing_metric_excluded_not_zeroed`。

### 5.5 已声明的局限

- **三层权重为等权平均**，未标定 —— 因为**没有数据支撑任何加权方案**。
  假装标定过权重比承认等权更不诚实。
- VLM 分数仍有小幅波动（已用 `temperature=0` + `seed=42` 缓解，用 L1 交叉验证）
- 未做人工盲评（时间预算外）

- 让 AI 生成代码很快，但"选 `animate-mix` 还是 I2V"、
  "评估要不要分三层"、"CI 公式的 k 取多少" —— 这些是**判断题**，
  必须自己想清楚。AI 只能提供选项和论据，不能给答案。

- 尤其是"用无 prompt 模型来保证可复用性"这个洞察：
  一般直觉会认为"没有 prompt 自由度 = 模型能力受限"，
  但**在本题语境下恰恰相反**，它成了防止特调的结构性保障。
  这种"反向思考"，AI 不会主动告诉我。

### 7.3 最花脑力的一个具体问题

> **"怎么证明这套 pipeline 是可复用的，而不是我嘴上说说？"**

尝试过的思路：
- ❌ 写文字声明"我们对 A/B 用同一配置" → 空口无凭，评审凭什么信？
- ❌ 展示代码 → 代码长，评审不会逐行看
- ✅ **发现三个可行方案，最后全做了**：
  1. **物理证据**：让 A/B/C 的 `runs/` 目录结构完全同构，`diff -r` 可验证
  2. **自动守卫**：写测试扫描 `stages/`，检测到片段特判就 fail
  3. **量化证据**：用 L3 跨片段方差直接给出一个数字

第 3 点最关键 —— **把"可复用性"这个抽象概念变成了一个可测量的数**。

## 八、失败案例分析

> 题面明确要求。以下区分三类：**做错了的** / **做不了的** / **还没做的**。

### 8.1 做错了的（已修正）

#### 失败案例 1：相对导入层级错误

**现象**：
```
ImportError: attempted relative import beyond top-level package
  config.py line 16: from ..errors import ConfigError
```

**原因**：`config.py` 位于包顶层 (`anime_pv/config.py`)，
`..errors` 会越出 `anime_pv` 包边界。正确写法是 `.errors`。

**根因分析**：写代码时套用了子包内的导入模式（`stages/x.py` 里用 `..errors` 是对的），
在顶层文件上想当然沿用了。

**修复**：改为 `from .errors import ConfigError`。

**教训**：**相对导入的层级取决于文件的深度，不能复制粘贴。**
应在生成代码后立刻做 import 冒烟测试，而不是写完所有文件才 import。

#### 失败案例 2：pip 源与 pip 版本不兼容

**现象**：
```
ERROR: Could not find a version that satisfies the requirement Pillow (from versions: none)
ERROR: No matching distribution found for Pillow
```
但 `curl` 访问同一个索引页返回 **HTTP 200**，页面内容正常。

**排查过程**：
1. 怀疑网络 → `curl` 索引页 200 ✅（网络没问题）
2. 怀疑索引内容 → Python `urllib` 直接拉页面，拿到 1.1MB HTML ✅（内容没问题）
3. 怀疑 pip 配置 → `pip config list` 显示指向清华源
4. 换阿里源 → **安装成功** ✅

**根因**：pip 26.1.2 与清华源的 simple 索引格式存在兼容问题
（较新的 pip 对 PEP 691 JSON 索引有依赖，部分镜像未适配）。

**修复**：换用 `https://mirrors.aliyun.com/pypi/simple/`，
并写进 `tools/setup_env.sh` 作为默认。

**教训**：**"网络通"不等于"pip 能装"。** 遇到 `No matching distribution`
且确认网络正常时，第一反应应该是**换源**，而不是继续查网络。

#### 失败案例 3：ffmpeg 安装的三连失败

| 尝试 | 结果 | 原因 |
|---|---|---|
| `winget install Gyan.FFmpeg` | ❌ | 创建符号链接失败：`create_symlink: The requested lookup key was not found`<br>（受限环境不允许创建 symlink），随后清理也 Access denied |
| 直接 `curl` GitHub Release | ❌ | `http=000`，GitHub 直连超时 |
| `ghproxy.net` 镜像 | ✅ | 成功下载 109MB |

**教训**：
1. **Windows 上 winget 装 ffmpeg 可能因 symlink 权限失败**，需备选方案
2. **GitHub 直连不可靠**，脚本里应内置多镜像轮询（已实现于 `tools/setup_ffmpeg.sh`）
3. 项目自带 ffmpeg（`tools/ffmpeg/`）比依赖系统 PATH 更可靠

#### 失败案例 4：ffmpeg 9.0.2 的 ffprobe 段错误（最有价值的发现）

**现象**：
```
$ ffprobe -v error -show_format -of json synth.mp4
Segmentation fault        (rc=139 / Windows 上 rc=3221225477)
$ ffprobe -version
Segmentation fault
```

**关键特征**：**连 `ffprobe -version` 都崩溃**，stdout 完全为空。

**排查过程**：
1. 最初以为是代码 bug → 直接在命令行手跑 `ffprobe`，同样段错误 → **排除代码问题**
2. 以为是视频文件损坏 → `ffprobe -version` 也崩 → **排除文件问题，是二进制本身的问题**
3. 判定为 **ffmpeg 9.0.2 nightly 构建在 Windows 上的缺陷**
4. **换用稳定版 6.1.1** → 恢复正常

**这是本项目最有价值的失败案例**，因为它揭示了一个反直觉的事实：

> **"最新版本"不等于"最可靠版本"。**
> 9.0.2 比 6.1.1 新三个大版本，但恰恰是新版的 ffprobe 崩了。
> 在工程实践中，**依赖应该锁稳定版，而不是追新**。

**修复措施（两层）**：

1. **降级依赖**：`tools/setup_ffmpeg.sh` 改用 6.1.1 稳定版
2. **加防御性兜底**（更重要）：`utils/video.probe()` 改为
   **ffprobe 优先 → 失败自动回退 OpenCV**：
   ```python
   def probe(path):
       if ffmpeg_available():
           try:
               return _probe_ffprobe(path)     # 优先精确探测
           except (...):
               pass                            # 崩了也不抛, 落到兜底
       return _probe_opencv(path)              # 兜底
   ```

**为什么第 2 条比第 1 条更重要**：
- 降级只解决了"这一个"版本的问题
- 兜底机制让管线**对探测工具的任何缺陷免疫** ——
  下次换任何 ffmpeg 版本，即使 ffprobe 出问题，管线仍能运行

**触发这个兜底的判据**（写在代码里）：
```python
if out.returncode != 0 or not (out.stdout or "").strip():
    raise InputValidationError(...)   # 段错误时 stdout 为空, 能可靠识别
```

**教训**：
1. **第三方二进制不可信，关键路径要有兜底**
2. **"连 `--version` 都崩"是判断"二进制本身损坏"的快速判据**，
   可以立刻把排查方向从"我的代码"转到"依赖工具"
3. 失败案例的价值不在于"我修好了"，而在于**提炼出可复用的防御模式**

**补充验证（6.1.1 装好后实测）**：

| 版本 | `ffprobe -version` | `ffprobe` 解析视频 | 结论 |
|---|---|---|---|
| 9.0.2 full_build | ❌ 段错误 rc=3221225477 | ❌ | 该版本专属缺陷 |
| 6.1.1 full_build | ✅ rc=0 | ✅ 正常 | 采用 |

同源（GyanD/codexffmpeg）、同架构（Windows x64）、同为 full_build，
唯一变量是版本号 —— 这就把"环境/架构/打包方式"全部排除，
**坐实了是 9.0.2 的版本缺陷**，而不是我们机器的问题。

另外补了一个**发现链上的次级失败**：`setup_ffmpeg.sh` 原来写死 9.0.2，
如果只改本地环境不改脚本，别人 clone 后照样踩同一个坑。
已把脚本 VERSION 钉到 6.1.1，并在安装末尾**加 `ffprobe -version` 健康自检** ——
把"装完就崩"提前到安装阶段暴露，而不是等跑管线才炸。

#### 失败案例 5：评估器自检机制形同虚设（隐蔽性最强）

**这是最危险的一类失败 —— 功能"看起来在工作"，实际完全没生效。**

**现象**：用 `smoke --jitter 0.6` 制造缺陷样本，评估结果和 `jitter=0` 一模一样：

```
jitter=0.0  -> 综合 89.74
jitter=0.6  -> 综合 89.74   ← 完全没变!
```

**根因（两个独立 bug 叠加）**：

| # | 位置 | 问题 | 危害 |
|---|---|---|---|
| 1 | `cli.cmd_smoke` | 硬编码 `build_adapter("mock", jitter=0.0)`，**忽略命令行 `--jitter`** | 缺陷样本根本没被制造 |
| 2 | `l1_technical.FlowSmoothnessEvaluator` | `score = 100*(1 - cv/0.8)` 线性硬截断 | CV>0.8 直接归零，指标失去分辨率 |

**Bug 1 的隐蔽性**在于：命令**没有报错**，跑得"很成功"，
产物目录、报告、CI 值全都正常产出 —— 只是那个 `--jitter` 参数被静默丢弃了。
如果没有"用已知缺陷验证评估器"这个自检动作，这个 bug 会一直藏着，
直到真实评估时给出**虚假的乐观结论**。

**Bug 2 的隐蔽性**在于：它和 Bug 1 的症状**重合** ——
两边表现都是"分数没变化"，很容易误判成只有一个问题。
实际上 `jitter=0` 的 passthrough 样本在旧公式下 `motion_smoothness` 也是 0.0，
说明这个指标在正常样本上就已经失效了。

**修复**：
1. `cmd_smoke` 透传 `args.jitter`，并在 jitter>0 时打印 `[扰动自检模式]` 提示
2. 光流归一化改为**指数饱和** `score = 100*exp(-cv/tau)`，`tau=1.2`：
   单调、无硬截断、在常见区间（CV 0.6~1.5）保持分辨率

**修复后验证**：

| 指标 | jitter=0（应满分） | jitter=0.6（应显著变差） | 有效? |
|---|---|---|---|
| psnr | 100.0 | **1.5** | ✅ |
| ssim | 100.0 | **51.1** | ✅ |
| temporal_stability | 98.0 | **0.0** | ✅ 抓到闪脸 |
| sharpness | 100.0 | **0.0** | ✅ 抓到模糊 |
| color_fidelity | 100.0 | **62.3** | ✅ 抓到亮度漂移 |
| motion_smoothness | 40.4 | 53.2 | ⚠️ 见下 |
| **综合** | **89.74** | **28.01** | ✅ 区分度 61.7 分 |

**教训（比案例 4 更重要）**：
1. **"跑通了"不等于"跑对了"**。评估器的自检必须用**已知缺陷**做，
   不能只看"有没有报错"。这正是 `tests/test_eval_sanity.py` 存在的理由。
2. **静默丢弃参数是最难查的 bug 类型** —— 不报错、不崩溃、结果看似合理。
   凡是 CLI 参数，都要有一条测试断言"它真的被用上了"。
3. `motion_smoothness` 在扰动样本上反而**变高**（40.4→53.2），
   乍看不合理，实际是**指标对扰动不敏感的可疑信号**：
   高斯模糊抹平了光流细节，让帧间运动幅值更"均匀"，CV 反而下降。
   这说明该指标**改进了归一化但仍不够稳健**，已在报告 §7 列为遗留风险。
   *（诚实记录：没有因为"总分已经能区分"就掩盖单项指标的异常。）*

### 8.2 做不了的（受客观限制）

#### 限制 1：无法做人物检测与精确占比对齐

**问题**：官方建议"确保输入图片与参考视频中人物画幅占比相似"。
我们的 `style_align` **只对齐画幅比例**（等比缩放 + 补边），
**不检测人物在画面中的实际位置和大小**。

**为什么做不了**：
- 需要额外的人体/人脸检测模型（如 YOLO、InsightFace）与调参时间
- 3 小时预算内无法可靠集成并验证

**影响**：若人设图中人物占比与 PV 中角色占比差异大，
仍会导致换人质量下降 —— 这正是官方所说的"最常见的弱结果原因"。

**缓解**：已在 `docs/02` 列为扩展点（`style_align` 增强）。

#### 限制 2：多角色场景必然失败

**问题**：平台模型针对**单一主角**替换。若 PV 片段中有多个角色同框，
模型无法区分该换谁。

**为什么做不了**：模型能力边界，非工程可解决。

**影响**：选片时必须避开多人镜头 —— 这也限制了可选片段范围。

**缓解**：在 `configs/clips.yaml` 的 `rationale` 字段里要求写明选片理由，
把"避开多角色"变成显式的选片标准。

#### 限制 3：音频不重生成

**问题**：只回接原片音轨，不做声音替换。
若人设角色与原角色性别/声线差异大，会有"音画不符"感。

**为什么不做**：题面只要求"人物替换"，未要求声音替换。
且需要额外的 TTS/音色转换模型，超出范围。

**缓解**：明确声明为范围外（`docs/00` §6），不假装做了。

#### 限制 4：无超分，输出固定 720P

**问题**：平台输出固定 720P，不做后处理提升。

**为什么不做**：时间预算外。Real-ESRGAN 等超分需要 GPU 与额外调参。

**影响**：成片分辨率低于原始 PV（若原片为 1080P）。

#### 限制 5：免费额度仅 50 秒

**问题**：换人模型 std + pro 模式**共享 50 秒免费额度**。

**影响**：若跑 A(6s) + B(6s) + C(8s) = 20 秒，一次完整跑就用掉 40%；
pro 模式出终稿还要再花 20 秒 → 额度基本用尽，**几乎没有重试空间**。

**缓解策略**：
1. std 模式跑通验证 → pro 只跑最终 1-2 个片段
2. 切片尽量短（5-6s）
3. 失败不扣费（可放心重试）

### 8.3 还没做的（诚实说明）

| 项目 | 原因 |
|---|---|
| 真实素材生成 | **等待用户提供 PV 与人设图**（按约定，素材由用户自备） |
| 成片与评估实测报告 | 依赖上一条 |
| 真实失败样本截图 | 依赖真实运行 |

| 三层权重标定 | 无数据支撑，刻意不做（见 §5.5） |

> **说明**：框架、评估体系、文档均已完成并**通过测试验证**
> （24 个测试全部通过）。
> 真实生成流程需素材就绪后执行，执行命令已在 README 中给出。

### 8.4 失败模式预测清单（基于官方文档）

以下是**预期中会遇到**的失败，素材就绪后需重点观察：

| 预期失败 | 官方依据 | 我们的检测手段 |
|---|---|---|
| 快速运镜 → 身份漂移 | "遮挡、剧烈运镜、低质输入可能导致身份漂移" | L2 `identity_consistency` + L1 `motion_smoothness` |
| 手部遮挡面部 → 闪烁 | "快速移动的物体会引入伪影和时序不稳定" | L1 `temporal_stability` |
| 人设占比不符 → 换人失败 | "画幅不匹配是最常见的弱结果原因" | 人工检视 + L2 各项 |
| 光照不融合 → 脸色不对 | Mix 模式靠 Relighting LoRA 适配光照 | L1 `color_fidelity` |
| 输出比原片更糊 | — | L1 `sharpness`（比值 < 1 即退化） |

> **片段 C 就是为此设计的压力测试样本**：刻意选高难度镜头（剧烈运镜/遮挡），
> 预期它会失败 —— 而**记录它怎么失败，比记录成功案例更有价值**。

## 九、结论

### 9.1 交付质量自评

| 维度 | 自评 | 依据 |
|---|---|---|
| 架构设计 | **优** | 五阶段解耦、模型可插拔、幂等、可诊断、有架构守卫测试 |
| 评估方案 | **优** | 三层完备、有自检机制、有诚实性约束、CI 公式实测有效 |
| 可复用性 | **优** | 无 prompt 自由度 + 无片段分支 + 测试自动守卫 + 量化指标 |
| 文档完整性 | **优** | 6 份文档，含决策论证而非仅描述 |
| 实测结果 | **待补** | 依赖素材与密钥 |

### 9.2 核心贡献

1. **把"可复用性"从口号变成了可测量的数** —— 一致性指数 CI
2. **把"公平性"从注意事项变成了架构组件** —— `style_align` 阶段
3. **把"评估可信"从假设变成了可验证的事实** —— 评估器自检测试
4. **用"减少自由度"保证"可复用性"** —— 选无 prompt 模型这个反直觉决策

### 9.3 一句话总结

> 这道题考的不是"能不能做出好看的视频"，
> 而是"**能不能设计出一套不挑片段的管线，并证明它不挑**"。
