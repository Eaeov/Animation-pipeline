# 需求分析文档

> 项目：动画 AI 管线（题 C）— 新番 PV 人物替换
> 版本：v1.0　|　日期：2026-09-23
> 配套：`TASK.md`（题面原文与硬约束）、`AGENTS.md`（AI 协作入口）

---

## 1. 任务本质还原

题面表面上说"跑个 pipeline 换个人"，但三句话暴露了真实考察点：

| 题面表述 | 真实考察 | 权重推断 |
|---|---|---|
| "侧重对结果质量的评估" | **你能不能定义"好"** | 高 |
| "侧重 pipeline 的设计和评估" | **架构能力**，不是调参能力 | 高 |
| "A/B 同 pipeline 都 75 分 > A/B 特调 90 分" | **可复用性 > 峰值质量** | **最高** |

**结论：这不是一个"生成任务"，是一个"工程 + 评估"任务。**

所以本项目的第一性目标是：

> 构建一条**参数化、可复现、对片段内容不敏感**的换人管线，
> 并用一套**能自证有效**的评估体系量化它的表现与稳定性。

反过来说，以下行为都是**明确失分**：
- 把整支 PV 全量跑一遍（题面点名"没有意义"）
- 为片段 A 写专属 prompt 拿到高分（违反可复用）
- 只出视频不出评估报告
- 只报"最好那个片段得了 90 分"

## 2. 需求分解

### 2.1 功能性需求（FR）

| ID | 需求 | 验收标准 |
|---|---|---|
| FR-1 | 从新番 PV 截取若干片段 | ≥2 个正式片段（A/B）+ 1 个压力片段（C），均满足平台约束 |
| FR-2 | 使用标准日式人设图 | 人设图为动漫风格角色立绘，合规且成功替换片中主角 |
| FR-3 | 人物替换生成 | 输出保留原片动作/场景/光照，主角被替换为人设角色 |
| FR-4 | 成片交付 | 每片段有 `final.mp4`（含音频）+ 对照视频 |
| FR-5 | 管线可独立运行 | 任一阶段可单独执行，支持断点续跑与缓存跳过 |
| FR-6 | 评估报告生成 | 三层评估（L1/L2/L3）自动产出 `report.md` + `report.json` |

### 2.2 非功能性需求（NFR）

| ID | 需求 | 验收标准 | 优先级 |
|---|---|---|---|
| NFR-1 | **可复用性** | A/B/C 走**完全同一套代码与配置**，无 `if clip_id == "A"` 分支 | **P0** |
| NFR-2 | **稳定性** | 跨片段指标标准差可量化且 ≤ 10 分（良好） | **P0** |
| NFR-3 | 可复现性 | 同输入 + 同配置 → 产物可重现；manifest 记录 input_hash | P1 |
| NFR-4 | 可诊断性 | 失败时能定位到 stage / clip / request_id | P1 |
| NFR-5 | 可扩展性 | 换模型只加 adapter；加指标只加 evaluator | P1 |
| NFR-6 | 成本可控 | 优先用免费额度，std 验证 → pro 终稿 | P2 |
| NFR-7 | 合规性 | 不提交密钥、不提交版权素材原文、标注素材来源 | P2 |

### 2.3 约束（Constraints）

**平台硬约束（不可协商）** — 详见 `TASK.md` §3.2：

- 参考视频：`2s < d ≤ 30s`、200–2048px、宽高比 1:3–3:1、≤200MB
- 人设图：200–4096px、宽高比 1:3–3:1、≤5MB
- 输入需公网可访问 URL
- 结果 URL 24h 失效
- 免费额度：换人 **50 秒**（std+pro 共享）；图片检测 200 张

**工程约束（自定）**：

- 3 小时完成
- 无 ffmpeg（需现装）
- 沙箱环境 pip 默认源不可用（需换阿里源）
- 结论必须可被证据支撑，禁止估算值填充

## 3. 关键设计决策（为什么这么设计）

### D1：为什么选「视频换人」而不是「首帧 I2V」

| 方案 | 保留原片运镜 | 跨片段一致性 | 可控性 | 结论 |
|---|---|---|---|---|
| 首帧 I2V | ✗ 会重绘背景 | 差（每段风格漂移） | 弱 | 淘汰 |
| 逐帧图生图 + 时序稳定 | ✓ | 中 | 中 | 工程量大，超时 |
| **视频换人 Mix** | ✓ **原生保留** | **好** | **强** | **选用** |

**核心理由**：视频换人做的是"替换主角"，背景/光照/动作全部继承自原片 ——
**跨片段的质量差异天然被压缩**，这正对 NFR-1/NFR-2 的要求。

### D2：为什么把「画幅对齐」独立成一个阶段

官方 FAQ 明确：*"确保输入图片与参考视频中人物画幅占比相似"* 是提升换人质量的第一建议，
且*"画幅不匹配是最常见的弱结果原因"*。

如果不对齐：A 片段可能因巧合匹配而高分，B 片段崩掉 —— **直接违反 P1**。
所以把"对齐"做成 **显式的、对 A/B 一视同仁的独立步骤**，而不是塞进 character 阶段里当副作用。

这是"用架构设计保证公平性"的具体体现。

### D3：为什么评估要分三层，且 L3 最重要

- **L1（客观）**解决"可复现"：不需要人、不需要 API、CI 可跑
- **L2（语义）**解决"任务本质"：L1 无法回答"人换成功了吗"
- **L3（稳定性）**解决"题目真正要什么"：**A/B 同 pipeline 的方差**

> **L3 是本题的胜负手**：只报单片段高分不作数，必须报跨片段方差。
> 我们把它编码成 `consistency_index = mean / (mean + 2*std)`，
> 同时惩罚"低分"和"高方差"，精确对应题面口径。

### D4：为什么必须有 Mock 适配器

三个现实原因：
1. 素材/密钥未就绪时，先验证框架结构正确
2. CI 回归测试不能真花钱
3. **评估器自检**：`MockAdapter(jitter=0.7)` 的退化产物必须让 L1 指标显著下降 ——
   如果评估器对人为扰动毫无反应，说明评估器是坏的

第 3 点是"评估方案本身可信"的证据。

## 4. 时间规划（3 小时）

| 时段 | 时长 | 任务 | 关键路径 | 产出 |
|---|---|---|---|---|
| 00:00–00:20 | 20m | 技术选型 + vibecoding 框架 | ★ | `AGENTS.md` / `ARCHITECTURE.md` / `TASK.md` |
| 00:20–00:45 | 25m | 需求分析文档（本文） | ★ | `docs/00-需求分析.md` |
| 00:45–01:05 | 20m | 代码骨架 + 依赖 + CLI | ★ | `src/` 可 import + `smoke` 通过 |
| 01:05–01:35 | 30m | 素材准备（PV 下载→切片→人设图） | ★★ | `assets/` + `configs/clips.yaml` |
| 01:35–02:05 | 30m | Pipeline 打通（std 模式，A/B/C） | ★★ | `runs/*/05_assemble/final.mp4` |
| 02:05–02:35 | 30m | 评估执行 + VLM 评分 + 报告 | ★★ | `report.md` + 证据图 |
| 02:35–02:55 | 20m | pro 模式终稿 + 失败案例归因 | ★ | 终稿视频 + 失败分析 |
| 02:55–03:00 | 5m | 文档收尾 + GitHub 发布 | ★ | 公开仓库 |

**关键路径**：`技术选型 → 素材准备 → Pipeline 打通 → 评估`（任一环卡住直接影响交付）。
框架搭建在前 1 小时完成，是为了让后面每一步都有工具支撑，而不是边写边调。

**风险与预案**

| 风险 | 概率 | 影响 | 预案 |
|---|---|---|---|
| 素材下载受阻 | 中 | 高 | 备用多个 PV 来源；极端情况用公开测试片源 |
| ffmpeg 缺失 | 高 | 中 | `cli doctor` 提前检出 + README 给安装命令 |
| 百炼图片检测不通过 | 中 | 中 | 换人设图；`check_image=false` 跳过预检 |
| 免费额度不够（50s） | 中 | 中 | 只跑 5-6s 短片段；先 std 后 pro |
| 生成排队超时 | 低 | 中 | 轮询间隔 15s、超时 900s；失败重试（失败不扣费） |
| VLM 评分不稳定 | 中 | 中 | 固定 temperature=0 + seed；交叉验证 L1 |

## 5. 验收标准

### 5.1 功能验收

- [ ] A、B、C 三个片段均产出 `final.mp4`
- [ ] `python -m anime_pv.cli smoke` 通过（离线，无需密钥）
- [ ] `python -m anime_pv.cli doctor` 报告环境状态
- [ ] 五阶段均可独立运行（`cli stage --stage X`）
- [ ] 评估报告含 L1 数值 + L2 评分 + **L3 稳定性数值**

### 5.2 核心指标验收（对应题目 P1）

| 指标 | 目标 | 说明 |
|---|---|---|
| 跨片段标准差 | ≤ 10 分 | 良好；≤5 优秀 |
| 一致性指数 CI | ≥ 0.85 | 越高越好 |
| 片段间极差 | ≤ 15 分 | 关键：特调 pipeline 的极差会很大 |
| A/B 使用同一配置 | 是 | 可用 `run_manifest.json` 的 config diff 证明 |

### 5.3 交付物验收

- [ ] GitHub 公开仓库，README 有快速开始
- [ ] `docs/` 六份文档齐全（需求/选型/Pipeline/评估/交付/素材来源）
- [ ] 结题 Markdown 回答题面 6 个问题
- [ ] 失败案例分析含**具体错误样本**，非泛泛而谈
- [ ] Token 消耗与个人耗时如实记录

## 6. 范围外（不做的事）

明确划出边界，避免范围蔓延：

| 不做 | 原因 |
|---|---|
| 跑完整支 PV | 题面点名"没有意义" |
| 自训练/微调模型 | 3 小时不可能，且题目允许用现成模型 |
| 音频替换/配音 | 题面只要求"人物替换" |
| 逐帧超分修复 | 超出时间预算；列为扩展点 |
| 多角色同时替换 | 平台模型限制，列为失败案例来源 |
| 为单片段特调参数 | **违反 P1，明确禁止** |
| 前端/演示页面 | 非交付物要求 |
