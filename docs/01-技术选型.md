# 技术选型文档

> 版本：v1.0　|　日期：2026-09-23
> 结论先行：**核心用阿里云百炼 `wan2.2-animate-mix`（万相-视频换人），
> 编排用自研 Python 五阶段管线，评估用「客观指标 + VLM + 跨片段方差」三层体系。**

---

## 1. 选型第一性原理

题目考察的是 **pipeline 设计与评估**，不是模型调参。
所以选型的评判标准不是"哪个模型单帧画质最高"，而是：

| 评判维度 | 权重 | 说明 |
|---|---|---|
| **跨片段一致性** | 40% | 对 A/B 用同一 pipeline 都能出片（题面 P1） |
| **可控性 / 变量少** | 25% | 输入变量越少，越容易做到参数化复用 |
| **保留原片结构** | 20% | 保留运镜/节奏/场景，才能叫"人物替换"而非"重做" |
| **成本与可获得性** | 10% | 3 小时预算 + 免费额度 |
| 单帧画质上限 | 5% | 够用即可，不是本项目目标 |

> 注意最后一行：**单帧画质上限被刻意降到最低权重**。
> 这是与"追求 90 分"路线的根本分野 —— 我们要的是稳定性。

## 2. 模型选型对比

### 2.1 候选方案

| 方案 | 机制 | 保留原片运镜 | 输入变量 | 跨片段一致性 | 成本 | 判定 |
|---|---|---|---|---|---|---|
| **万相-视频换人**<br>`wan2.2-animate-mix` | 人设图 + 参考视频 → 替换主角 | ✓ 原生保留 | **2 个**（图、视频） | **高** | 0.6/0.9 元/秒<br>**免费 50s** | ✅ **选用** |
| 万相-图生动作<br>`wan2.2-animate-move` | 人设图 + 动作参考 → 重新生成场景 | ✗ 背景改由图片决定 | 3 个（+背景描述） | 中 | 同上 | ✗ 会丢原片场景 |
| 图生视频-首帧<br>`wan2.2/2.5/2.6-i2v` | 首帧图 + prompt → 视频 | ✗ 完全重绘 | 2 个但含 prompt | **低** | 0.24 元/秒起 | ✗ prompt 敏感性高 |
| 图生视频-首尾帧 | 两帧约束 | 部分（仅首尾） | 3+ | 中 | 较高 | ✗ 需额外造尾帧 |
| 参考生视频 | 多视频参考角色 | ✗ | 多 | 中 | 较高 | ✗ 面向复刻角色非替换 |
| 逐帧图生图 + 光流稳定 | 每帧换脸 | ✓ | 多 | 中 | 自建 | ✗ 3 小时不可行 |

### 2.2 为什么 `animate-mix` 胜出（三条硬理由）

**理由 1：它做的是"替换"而不是"重绘"。**
官方定义：*"在不改变原始视频的动作、表情及环境的条件下，将视频中的角色替换为指定图片中的人物"*。
输出 = 原片场景 + 原片动作 + 新角色。**背景/光照/运镜由原片继承** ——
这直接消除了"跨片段风格漂移"这个最大的一致性杀手。

**理由 2：输入变量只有 2 个。**
`image_url` + `video_url`。**没有 prompt 自由度**意味着：
- 不存在"为片段 A 特调 prompt"的空间（架构上就杜绝了违规）
- A/B/C 天然走过同一条代码路径（NFR-1 达成）
- 变量少 → 方差小 → NFR-2 达成

> 这是一个关键洞察：**用"减少自由度"来保证可复用性。**
> 对比 I2V 方案，prompt 是个巨大的自由度，很容易滑向"为每段调 prompt"的歧路。

**理由 3：成本可忽略。**
58 秒免费额度（换人 50s + 检测 200 张免费）足以覆盖 3 个 6-8s 片段的多轮迭代。
超出后 std 模式 0.6 元/秒，跑一轮 A/B 仅约 7 元。

### 2.3 采用的模型清单

| 用途 | 模型 | 单价 | 免费额度 |
|---|---|---|---|
| 人物替换（主） | `wan2.2-animate-mix` | std 0.6 元/秒 / pro 0.9 元/秒 | 50 秒（共享） |
| 语义评估 | `qwen-vl-max` | 按 token | 有额度 |
| （可选）人脸相似度 | `insightface` 本地 | 0 | — |

## 3. 平台约束与技术风险

### 3.1 约束清单（决定 pipeline 结构）

| 约束 | 值 | 对设计的影响 |
|---|---|---|
| 视频时长 | `2s < d ≤ 30s` | **必须切片** → 催生 `ingest` 阶段 |
| 视频分辨率 | 200–2048px | 需归一化 → `normalize()` |
| 视频大小 | ≤200MB | 需检查 → 预检机制 |
| 图片大小 | ≤5MB | 需压缩 → `utils/image.normalize()` |
| 宽高比 | 1:3–3:1 | 需补边 → `style_align` 阶段 |
| 输入格式 | 需公网 URL | 需上传中转 → `publisher` 抽象 |
| 结果时效 | 24h | 必须立即下载转存 |
| 输出规格 | 720P, std 15fps / pro 25fps | std 先验证，pro 出终稿 |

### 3.2 质量风险与对策

**官方给出的失败模式（这是我们的失败案例预测清单）：**

| 官方提示 | 我们的对策 | 对应失败案例 |
|---|---|---|
| "确保输入图片与参考视频中人物画幅占比相似" | **独立 `style_align` 阶段** | 画幅不匹配 → 换人失败 |
| "保持图片和视频中人物的身材比例一致" | 记录在 clips.yaml 的 rationale | 身材比例失调 |
| "使用高清素材，避免模糊图片和低帧率视频" | ingest 归一化 + 质量预检 | 低质输入 → 脸糊 |
| 「遮挡、剧烈运镜、低质输入 → 身份漂移」 | 片段 C 专门选高难度样本 | 快速运镜 → 身份漂移 |
| 「复杂交互/快速移动道具会引入伪影」 | L1 的 `temporal_stability` 专门检测 | 手部遮挡 → 闪烁 |

> 注意：**这些风险不是猜测，是官方文档明示的**。
> 把它们逐条转成"对策 + 待验证案例"，本身就是评估方案设计的一部分。

## 4. 技术栈选型

| 层 | 选型 | 理由 | 备选与否决 |
|---|---|---|---|
| 语言 | Python 3.13 | AI 生态、库齐全 | — |
| HTTP | `requests` | 简单够用，百炼是 REST | ✗ httpx（异步用不上，增加复杂度） |
| 视频处理 | **ffmpeg** CLI + OpenCV | ffmpeg 精确切片/拼接；cv2 做帧级分析 | ✗ moviepy（封装厚、调试难） |
| 图像处理 | Pillow + OpenCV | Pillow 做规整，cv2 做指标 | — |
| 配置 | YAML | 可读性好，非程序员也能改 | ✗ JSON（不能写注释） |
| 指标 L1 | `scikit-image`(SSIM) + 自研 | 轻量，无 torch 依赖 | ✗ torchmetrics/LPIPS（体积大，VLM 已补语义层） |
| 指标 L2 | 百炼 VLM（`qwen-vl-max`） | 直接复用已有密钥 | ✗ 本地 VLM（6G 显存不够） |
| 编排 | **自研轻量管线** | 阶段解耦、manifest 可追溯、无框架学习成本 | ✗ Airflow/Prefect（3 小时学不完，杀鸡用牛刀）<br>✗ Dify（面向对话流非媒体管线） |
| 报告 | Markdown + JSON 双出 | md 给人看，json 给程序统计 | — |

### 为什么不用编排框架（值得说明）

考虑过 Airflow / Prefect / LangChain，最终否决，理由：

1. **3 小时预算**装不下框架的环境与概念成本
2. 本管线只有 5 个阶段，**线性依赖**，自研 `PIPELINE` 列表足够
3. 自研能精确控制 **manifest 结构**（这是可复现性的核心，框架的元数据往往不合身）
4. 自研能实现**阶段独立运行 + 幂等缓存**，这恰好是 NFR-1/NFR-3 的要求

> 结论：**不必要的抽象是负债。** 5 个阶段不值得引入 DAG 调度器。

## 5. 为什么是「publisher 抽象」而不是直接传 URL

百炼要求输入是公网 HTTP(S) URL，但我们的素材在本机。三种解法：

| 方案 | 优点 | 缺点 | 采用 |
|---|---|---|---|
| data URI (base64) | 零配置 | 200MB 视频会爆掉请求体 | 兜底实现 |
| OSS 上传 | 官方推荐、稳定 | 需额外 AK 配置 | 扩展点（`adapters/cdn.py`） |
| 临时图床 | 简单 | 不稳定、可能违反 ToS | ✗ |

→ 抽象成 `Publisher` 协议，**换实现不改 stage**。这是 NFR-5 的落地方式。

## 6. 选型结论汇总

```
输入素材（本地）
    ↓ 切片 + 归一化          [stages/ingest]
    ↓ 人设图规整             [stages/character]
    ↓ 画幅对齐（保证公平）    [stages/style_align]
    ↓
万相-视频换人 wan2.2-animate-mix   ← 核心模型
    ↓ 音频回接 + 对照视频     [stages/assemble]
    ↓
成片
    ↕
三层评估：L1 客观 / L2 语义(VLM) / L3 跨片段方差   ← 核心资产
```

**一句话总结选型逻辑：**
> 选一个**输入变量最少、原生保留原片结构**的模型，
> 用**显式的对齐阶段**消除片段间差异，
> 用**跨片段方差指标**把"可复用性"变成可测量的数字。

## 7. 备选方案（若主方案受阻）

| 场景 | 备选 |
|---|---|
| `animate-mix` 不可用 | `wan2.2-animate-move`（换背景但动作可迁移） |
| 免费额度耗尽 | 降价到 std 模式 + 缩短片段至 5s；仍不够则只跑 A/B 不跑 C |
| 素材替换失败率高 | 换用更"正面、无遮挡"的 PV 片段（调整 `clips.yaml`） |
| 需要更高画质 | 加 `stages/06_upscale`（Real-ESRGAN），已列为扩展点 |
